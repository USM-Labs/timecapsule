# ADR-0005. Где хранить сессии пользователей: таблица Amazon DynamoDB

- Статус: принято
- Дата: 2026-11-23
- Связано с: [ADR-0003](0003-attachment-storage.md) (вложения в S3), [ADR-0004](0004-database-hosting.md) (база в RDS)

## Контекст

После ЛР4 и ЛР5 вложения лежат в S3, данные в RDS, и на диске `app-server` осталось одно состояние - PHP-сессии в `storage/sessions/` (кто вошёл и CSRF-токен формы). В ЛР6 приложение уходит за Application Load Balancer в группу Auto Scaling из 2-4 серверов в двух зонах. Балансировщик отправляет каждый запрос на любой исправный сервер, а группа сама добавляет, удаляет и заменяет серверы.

Требования:

- пользователь не должен терять вход, на какой бы сервер ни попал запрос и что бы ни происходило с группой (рост, уменьшение, замена нездорового сервера, отказ зоны);
- серверы должны оставаться одинаковыми и одноразовыми: их можно удалить в любой момент без потери данных;
- без ключей доступа в коде и `.env`, минимальные права;
- стоимость - доли цента при учебной нагрузке, без отдельных серверов;
- минимальная правка кода (вариант `open_capsules_php_functional`).

## Рассмотренные варианты

| Вариант | Как работает | Плюсы | Минусы |
| --- | --- | --- | --- |
| **A. Файлы на сервере + sticky sessions** | Сессия остаётся в `storage/sessions/`; у целевой группы включено `Stickiness` (cookie `AWSALB`), и балансировщик отправляет пользователя всё время на один сервер | Код не меняется, нет новых сервисов | Сессия умирает вместе с сервером: при уменьшении группы, замене по health check или отказе зоны пользователя выкидывает. Нагрузка распределяется неровно (новые серверы получают только новых пользователей), что мешает и масштабированию по `RequestCountPerTarget`. Серверы перестают быть одноразовыми |
| **B. Таблица в RDS** (`sessions` в PostgreSQL) | Свой `SessionHandlerInterface` или готовый PDO-обработчик, одна строка на сессию | Общий для всех серверов, база уже есть | Каждый запрос к любой странице делает чтение и запись в базу, нагрузка на единственный `db.t4g.micro` растёт с числом пользователей. Сессии исчезают, когда база остановлена ночью или перезагружается (и вход вместе с ними, хотя страницы всё равно не работают). Удаление старых сессий - своя задача по расписанию. Нужен свой код обработчика и миграция таблицы |
| **C. Таблица DynamoDB** | `Aws\DynamoDb\SessionHandler` из уже подключённого AWS SDK, элемент на сессию, ключ `id`, TTL `expires` | Общая для всех серверов, без серверов и обслуживания, задержка единицы миллисекунд, On-demand стоит доли цента, TTL сам удаляет истёкшие сессии, права IAM на одну таблицу, правка - ~15 строк в `bootstrap.php` | Ещё один сервис и политика IAM; нет блокировок сессии по умолчанию (параллельные запросы одного пользователя могут перезаписать друг друга - для этого приложения не важно); локальная разработка без AWS остаётся на файлах |

## Решение

Вариант **C**. Таблица `timecapsule-dev-sessions` (ключ раздела `id` String, режим On-demand, TTL по атрибуту `expires`). В `src/bootstrap.php` перед `session_start()` регистрируется `Aws\DynamoDb\SessionHandler::fromClient()` с `table_name` из `SESSIONS_TABLE`, `hash_key=id`, `session_lifetime_attribute=expires`, `session_lifetime=3600`. Если `SESSIONS_TABLE` пустая (локальный Docker), сессии остаются файлами.

Учётные данные SDK берёт из роли `timecapsule-dev-app-role` (instance profile, IMDSv2). Политика `timecapsule-dev-app-sessions` разрешает только `dynamodb:GetItem`, `PutItem`, `UpdateItem`, `DeleteItem` на ARN этой таблицы - ни `Scan`, ни `DeleteTable`, ни других таблиц.

Sticky sessions на `timecapsule-dev-tg` выключены.

## Последствия

- Серверы группы взаимозаменяемы: образ `timecapsule-dev-app-lab6` содержит код и `.env`, состояние - в RDS, S3 и DynamoDB. Проверено в ЛР6: при росте группы с 2 до 4 серверов запросы попадали на новые серверы (`ip-10-16-0-50`), вход сохранялся.
- Каждый запрос страницы делает 1 чтение и 1 запись в DynamoDB. При On-demand это ≈ $0,25 за миллион чтений и ≈ $1,25 за миллион записей - для учебного трафика доли цента. Хранение - килобайты.
- Истёкшие сессии удаляет TTL (обычно в течение суток после `expires`); до удаления `SessionHandler` сам не принимает просроченную сессию.
- Значение cookie `timecapsule_session` - это ключ элемента. Кто получил cookie, тот получил сессию, поэтому cookie `HttpOnly` и `SameSite=Lax`; следующий шаг - HTTPS на балансировщике (ACM-сертификат) и флаг `Secure`.
- При отказе зоны `eu-central-1a` таблица продолжает работать (DynamoDB регионального уровня, данные в трёх зонах), серверы в `1b` обслуживают всех пользователей без повторного входа. Остаётся зависимость от базы в `1a` (ADR-0004).
- Блокировок нет: если пользователь шлёт два запроса одновременно, побеждает последняя запись. Для TimeCapsule (вход и CSRF-токен) это допустимо; при сложном состоянии в сессии нужно включить `locking` в `SessionHandler` (дороже по запросам).
