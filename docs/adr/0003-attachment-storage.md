# ADR-0003. Хранение вложений капсул: бакет Amazon S3 и подписанные ссылки

- Статус: принято
- Дата: 2026-10-29
- Связано с: [ADR-0002](0002-database-placement.md) (база на отдельном сервере в приватной подсети)

## Контекст

После ЛР3 база TimeCapsule живёт на `timecapsule-dev-db`, а вложения капсул (картинки и PDF до 5 МБ)
по-прежнему лежат в `storage/uploads` на корневом томе EBS `timecapsule-dev-app`. PHP читает файл с диска
и сам отдаёт его браузеру. Из-за этого `app-server` хранит данные пользователей: его нельзя просто заменить
новым (файлы пропадут при Terminate) и рядом нельзя поставить второй сервер (у него не будет этих файлов).

Требования:

- вложение видит только владелец капсулы (или все, если капсула публичная) и только после открытия;
- файлы должны пережить замену или потерю сервера приложения;
- случайное удаление или перезапись файла можно отменить;
- стоимость хранения не растёт бесконечно;
- никаких ключей доступа в коде и `.env`, репозиторий публичный.

## Решение

Вложения хранятся в бакете `timecapsule-dev-uploads-maxsplavski` (`eu-central-1`) под ключами
`uploads/<случайное имя>`. Бакет закрыт: `ACLs disabled`, `Block all public access`, шифрование SSE-S3,
политика бакета запрещает любые запросы без HTTPS (`aws:SecureTransport = false`).

- **Запись и удаление.** Модуль [`src/storage.php`](../../src/storage.php) вызывает `putObject` (с
  `ContentType` файла) и `deleteObject` через AWS SDK for PHP. Учётные данные SDK берёт из роли сервера
  `timecapsule-dev-app-role` (instance profile), а не из `.env`.
- **Права приложения.** Политика `timecapsule-dev-app-s3` (версия 2) разрешает только `s3:GetObject`,
  `s3:PutObject`, `s3:DeleteObject` на `arn:aws:s3:::timecapsule-dev-uploads-maxsplavski/uploads/*`.
  Списка объектов нет, удалять версии нельзя.
- **Чтение.** Приложение проверяет права пользователя на капсулу и отвечает `302` на подписанный URL
  `GetObject` сроком 5 минут с `ResponseContentType` и `ResponseContentDisposition` (inline/attachment и
  исходное имя файла). Браузер скачивает файл прямо из S3, PHP через себя его не пропускает.
- **Защита и стоимость.** Включено версионирование; правило `timecapsule-dev-noncurrent` для `uploads/`
  переводит неактуальные версии в Standard-IA через 30 дней, удаляет их через 90 дней (две самые новые
  оставляет) и удаляет незавершённые загрузки частями через 7 дней.

## Рассмотренные альтернативы

- **Диск EBS сервера приложения (как в ЛР2-ЛР3).** Проще всего, без новых сервисов и SDK. Отказались:
  том привязан к одному экземпляру в одной AZ, при Terminate по умолчанию удаляется; второй сервер файлов
  не увидит; резервные копии только снапшотами всего тома; каждую загрузку и скачивание обрабатывает PHP,
  занимая воркер PHP-FPM на всё время передачи.
- **Общая файловая система Amazon EFS.** Код почти не меняется: EFS монтируется в `storage/uploads`
  на всех серверах (NFS), доступна из нескольких AZ. Отказались: за ГБ на порядок дороже S3 (EFS Standard порядка $0,3 за
  ГБ-месяц против ~$0,0245 у S3 Standard во Франкфурте), нужны mount targets в подсетях и Security Group для NFS (2049), файлы по-прежнему
  отдаёт PHP, нет версий объектов и подписанных ссылок, а сервер всё равно зависит от смонтированного диска.
- **Бакет Amazon S3 (выбрано).** Хранилище вне VPC и вне серверов, 11 девяток долговечности, оплата только
  за объём и запросы, версионирование, жизненный цикл, подписанные URL. Цена: зависимость от AWS SDK,
  права через IAM, изменение модуля хранения и вопросы срока жизни ссылок.

## Последствия

- **Как пользователь получает файл.** Браузер запрашивает `/capsules/{id}/file`, приложение проверяет
  сессию, владельца или публичность и что капсула открыта, затем отдаёт `302` на подписанную ссылку.
  Срок ссылки ограничен двумя вещами: `X-Amz-Expires=300` (5 минут, задано в коде) и сроком временных
  учётных данных роли, которыми ссылка подписана (обычно несколько часов). Ссылку нельзя изменить
  (`SignatureDoesNotMatch`) и после срока она не работает (`Request has expired`), отзывать её не нужно.
  Сам ответ `302` помечен `Cache-Control: no-store`.
- **Защита от случайного удаления.** Версионирование: удаление в приложении ставит маркер удаления,
  прежняя версия остаётся и восстанавливается удалением маркера. Роль приложения не может удалять версии
  (`s3:DeleteObjectVersion` не разрешён), поэтому даже с её учётными данными нельзя уничтожить файлы
  без возврата. Против ошибок администратора можно добавить MFA Delete или Object Lock.
- **Ограничение стоимости.** Правило `timecapsule-dev-noncurrent`: старые версии через 30 дней в
  Standard-IA, через 90 дней удаляются (кроме двух новых), незавершённые multipart-загрузки - через 7 дней.
  Мелкие объекты меньше 128 КБ в Standard-IA не переходят (минимальный размер перехода). Бюджет `ZeroSpend`
  сообщит о любых расходах.
- **Несколько серверов и балансировщик.** Серверы приложения становятся одинаковыми и не хранят
  состояния: каждый получает ту же роль `timecapsule-dev-app-role` через launch template, файлы и база
  общие. Их можно запускать в Auto Scaling Group за ALB в `public-a`/`public-b` (а сами серверы - в
  приватных подсетях). Тогда нужен путь из приватных подсетей в S3 - бесплатный Gateway VPC endpoint для S3
  (а не NAT), и в политику бакета можно добавить условие `aws:SourceVpce`. Сессии PHP пока лежат в
  `storage/sessions` на диске, их тоже надо вынести (ElastiCache или база) или включить sticky sessions.
- **Минусы.** Файлы на время 5 минут доступны любому, у кого есть ссылка. Нужен интернет-доступ к S3 у
  сервера (сейчас через Internet Gateway публичной подсети). Локальный запуск через Docker без AWS теперь
  требует бакета и учётных данных (или эмулятора S3).
