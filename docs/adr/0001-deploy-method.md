# ADR-0001. Доставка кода на сервер: скрипт `deploy.sh`, запускаемый по SSH

- Статус: принято
- Дата: 2026-10-29

## Контекст

TimeCapsule (PHP 8.4, PostgreSQL 16) работает на одном экземпляре EC2 `webserver`
(t3.micro, Amazon Linux 2023, `eu-central-1`). Единственный источник кода - публичный
репозиторий `USM-Labs/timecapsule` на GitHub. Выпуск новой версии состоит из одних и тех же
шагов: забрать код, установить библиотеки Composer по `composer.lock`, создать недостающие
таблицы (`bin/init-db.php`) и перезагрузить PHP-FPM.

Ограничения:

- команда из одного человека, без CI/CD-сервиса (он появится позже в курсе);
- сервер должен только читать репозиторий: прав на запись в GitHub у него быть не должно;
- секреты (`.env` с паролем к базе) живут только на сервере и не попадают в git;
- выпуск должен быть повторяемым, а при ошибке сразу останавливаться и показывать, на каком шаге он упал.

## Решение

Выпускаем версии скриптом `~/deploy.sh` на сервере (копия лежит в репозитории: `deploy/deploy.sh`).
Скрипт выполняет `git pull --ff-only`, `composer install --no-dev --optimize-autoloader`,
`php bin/init-db.php` и `sudo systemctl reload php-fpm`, работает в режиме `set -euo pipefail` и
в конце печатает коммит, который теперь работает на сервере.

Разработчик запускает его со своего компьютера одной командой, не заходя на сервер:

```bash
ssh -i ~/.ssh/maxsplavski-keypair.pem ec2-user@<Public-IP> ./deploy.sh
```

Сервер скачивает код по HTTPS без учётных данных: репозиторий публичный, поэтому доступ только на чтение.
Откат делается через репозиторий (`git revert` → `git push` → `deploy.sh`), а не правкой файлов на сервере.

## Рассмотренные альтернативы

- **Копирование файлов через `scp`** (как в Части 1). Самый простой способ, на сервере не нужен git.
  Отказались: непонятно, какая версия кода работает на сервере; легко забыть файл; нет истории и
  нормального отката; `vendor/` пришлось бы собирать локально и копировать целиком; код живёт на
  ноутбуке, а не в общем репозитории.
- **`git pull` вручную на сервере (вариант A).** Версия однозначно определяется коммитом, откат через
  `git revert`. Отказались: каждый раз нужно заходить по SSH и набирать четыре-пять команд в правильном
  порядке, легко пропустить `composer install` или перезагрузку PHP-FPM; без `set -e` ошибка на одном
  шаге не останавливает следующие.
- **Скрипт `deploy.sh` (выбрано).** Те же шаги, что в варианте A, но записанные один раз и выполняемые
  одинаково, с остановкой при первой ошибке и отчётом о версии. Запускается удалённо одной командой
  `ssh ... ./deploy.sh`, это первый шаг к автоматизации.
- **CI/CD (GitHub Actions, AWS CodeDeploy)** - выпуск по `git push` без участия человека. Пока не
  используем: эти инструменты в курсе ещё не пройдены, для одного сервера и одного разработчика это
  избыточно, а для GitHub Actions пришлось бы хранить SSH-ключ к серверу в секретах организации.

## Последствия

- Плюс: на сервере всегда известный коммит (`git log -1`), выпуск и откат повторяемы и занимают
  несколько секунд; в эксперименте задания 13 сломанная версия проработала около 37 секунд
  (деплой сломанного коммита закончился в 00:09:30 UTC, деплой отката в 00:10:07 UTC).
- Плюс: сервер не может изменить код в репозитории; секреты остаются в `.env` на сервере.
- Минус: выпуск не атомарный. `git pull` меняет файлы по одному, и на несколько секунд код и
  `vendor/` могут не совпадать. Если упадёт `composer install`, сайт останется с новым кодом и
  старыми библиотеками. Решение на будущее: выкладка в отдельную папку `releases/<commit>` и
  переключение симлинка `current`.
- Минус: нет проверок перед выпуском. Синтаксическая ошибка в `views/layout.php` дошла до продакшена,
  а `/health` продолжал отвечать `ok`, потому что проверяет только PHP и базу, а не рендер страниц.
  Нужны `php -l` / тесты в CI и smoke-тест главной страницы после деплоя с автоматическим откатом.
- Риск: деплой запускает человек вручную, и ему нужен приватный SSH-ключ и доступ по 22 порту с его IP.
  Публичный IP меняется после остановки экземпляра, поэтому адрес в команде нужно обновлять
  (решается Elastic IP или DNS).
- Риск: один экземпляр без резервных копий. База и загруженные файлы живут на корневом томе EBS и
  будут потеряны вместе с экземпляром при Terminate (том удаляется по умолчанию).
