# ADR-0002. Размещение базы данных: отдельный сервер в приватной подсети

- Статус: принято
- Дата: 2026-10-29
- Связано с: [ADR-0001](0001-deploy-method.md) (деплой через `deploy.sh`)

## Контекст

В ЛР2 TimeCapsule жил на одном экземпляре EC2 в default VPC: nginx, PHP-FPM и PostgreSQL на одной машине
с публичным адресом, база слушала `localhost`. Для ЛР3 построена собственная сеть `timecapsule-dev-vpc`
(`10.16.0.0/16`) с публичными подсетями `public-a/b` (маршрут в `timecapsule-dev-igw`) и приватными
`private-a/b` (только маршрут `local`). Нужно решить, где будет работать PostgreSQL.

Требования и ограничения:

- база не должна быть доступна из интернета ни при какой ошибке в одном из фильтров;
- приложение должно находить базу по имени, а не по адресу;
- бюджет студенческий: постоянный NAT Gateway (~$1,25 в сутки) дороже всех серверов вместе;
- управляемые сервисы (RDS) в курсе ещё не пройдены.

## Решение

PostgreSQL 16 работает на отдельном экземпляре `timecapsule-dev-db` в приватной подсети
`timecapsule-dev-private-a` (`10.16.10.184`), без публичного адреса. Защита в несколько слоёв:

1. **Маршрут и адрес.** У `private-rt` нет маршрута в Internet Gateway, у сервера нет публичного IP:
   из интернета до него нет пути, а сам он в интернет не выходит.
2. **Security Group `timecapsule-dev-db-sg`.** Порт 5432 открыт только для группы `timecapsule-dev-web-sg`,
   SSH - только из `timecapsule-dev-bastion-sg`.
3. **`pg_hba.conf`.** Вход по `scram-sha-256` только пользователю `timecapsule` в базу `timecapsule`
   и только из `10.16.0.0/24` (`public-a`). У пользователя новый сильный пароль, не из ЛР2.

Приложение (`timecapsule-dev-app` в `public-a`, Elastic IP) обращается к базе по имени
`db.timecapsule.internal` из приватной зоны Route 53, которая видна только внутри VPC.

## Рассмотренные альтернативы

- **На одном сервере с приложением (как в ЛР2).** Дёшево и просто: один экземпляр, база на
  `localhost`, никаких сетевых правил. Отказались: взлом веб-сервера сразу даёт доступ к файлам базы;
  приложение и база конкурируют за CPU и память одного t3.micro; масштабировать приложение на несколько
  серверов нельзя, потому что база привязана к одному из них; обновлять и перезагружать их по отдельности
  невозможно.
- **Отдельный сервер в публичной подсети.** Пакеты ставятся напрямую через Internet Gateway, NAT не нужен.
  Отказались: у сервера есть публичный адрес и маршрут из интернета, и от утечки базы отделяет только
  одно правило Security Group. Одна ошибка (например, источник `0.0.0.0/0` вместо `web-sg`) открывает порт
  5432 всему интернету, а такие порты постоянно сканируют.
- **Отдельный сервер в приватной подсети (выбрано).** Чтобы добраться до базы, нужно одновременно
  обойти маршрутизацию, Security Group и `pg_hba.conf` с паролем. Цена этого - отдельный экземпляр,
  bastion для администрирования и временный NAT Gateway для обновлений.
- **Amazon RDS for PostgreSQL** (вне рамок текущей работы). Резервные копии, патчи и Multi-AZ берёт на
  себя AWS. Пока не используем: сервис ещё не пройден в курсе, а у free tier есть ограничения. Это
  естественный следующий шаг; при переходе на RDS база останется в приватных подсетях `private-a/b`
  (DB subnet group), а имя `db.timecapsule.internal` станет CNAME на endpoint RDS.

## Последствия

- **Обновления без постоянного выхода в интернет.** У `db-server` нет пути в интернет, поэтому
  `dnf update` работает только при поднятом временном NAT Gateway. Его создаёт
  [`scripts/nat-up.sh`](../../scripts/nat-up.sh) (Elastic IP + NAT в `public-a` + маршрут `0.0.0.0/0` в
  `private-rt`), а после обновления удаляет [`scripts/nat-down.sh`](../../scripts/nat-down.sh). NAT
  стоит около $0,052 в час (eu-central-1) плюс $0,052 за ГБ трафика, Elastic IP - $0,005 в час. Сеанс
  обновления на 15-20 минут обходится в 1-3 цента против ~$38 в месяц за постоянный NAT. Минус: обновления
  ставятся только когда кто-то запускает скрипты, автоматических патчей нет. Альтернатива на будущее -
  VPC endpoint к репозиториям через S3 или собственное зеркало пакетов.
- **Elastic IP у `app-server`.** Публичный адрес экземпляра меняется при каждом Stop/Start, а адрес
  приложения записан в `APP_URL` в `.env` и в закладках пользователей. Elastic IP
  `timecapsule-dev-app-eip` (`63.189.89.102`) закрепляет адрес. Он оплачивается всегда, даже у
  остановленного сервера (~$3,6 в месяц). Bastion Elastic IP не нужен: его адрес нужен только
  администратору, и `HostName` в `~/.ssh/config` легко обновить.
- **Когда появится балансировщик (ALB).** Пользователи будут обращаться к DNS-имени балансировщика, а
  `app-server` можно будет перенести в приватные подсети без публичного адреса. Elastic IP станет не нужен,
  его надо будет освободить; `web-sg` будет пускать порт 80 только от группы балансировщика. Балансировщику
  нужны подсети минимум в двух AZ - `public-a` и `public-b` для этого уже готовы.
- **Плюс:** база отделена от приложения: отказ или перезапуск `db-server` не трогает сервер приложения
  (проверено в задании 13: после Stop/Start базы приложение восстановилось само, приватный IP не изменился).
  Можно добавлять серверы приложения, все они ходят к одной базе по имени.
- **Минус:** больше ресурсов и сетевых правил, все SSH-подключения идут через bastion. Запрос к базе теперь
  проходит по сети (небольшая задержка), а при недоступности базы приложение около 5 секунд ждёт таймаута
  подключения и отвечает 500.
- **Риск:** база в одном экземпляре в одной AZ (`eu-central-1a`), без реплики. Данные на одном томе EBS:
  нужны регулярные снапшоты или `pg_dump` в S3. Загруженные файлы по-прежнему лежат на диске `app-server`
  (`storage/uploads`), а не рядом с базой; их тоже надо будет вынести (S3).
