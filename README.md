> **Что разрешает политика `AdministratorAccess`? Почему для повседневной работы нельзя использовать root?**
> `AdministratorAccess` разрешает все действия (`"Action": "*"`) над всеми ресурсами (`"Resource": "*"`), но это обычная политика IAM: её можно отозвать, ограничить SCP или permission boundary, а действия пользователя видны в CloudTrail под его именем. Root - владелец аккаунта, его права нельзя ограничить, он может закрыть аккаунт, сменить платёжные данные и план поддержки. Утечка пароля или ключей root означает потерю всего аккаунта, поэтому root используют только для редких задач, которым он нужен именно сам, и защищают MFA.

![Instance screenshot](docs/screenshots/03-instance-screenshot.jpg)

> **Какая из проверок укажет на проблему, которую можете исправить вы, а какая на проблему на стороне AWS?**
> _System status check_ проверяет инфраструктуру AWS (физический хост, питание, сеть): при её сбое исправлять должна AWS, а пользователь может только перенести экземпляр на другой хост через Stop/Start. _Instance status check_ проверяет саму ОС: неверная сетевая конфигурация, переполненный диск, паника ядра, ошибка в fstab. Это проблемы, которые исправляет владелец экземпляра. _Attached EBS status check_ показывает недоступность подключённых томов EBS, обычно это проблема на стороне AWS.

> **В каких случаях стоит включать детальный мониторинг?**
> Когда важна быстрая реакция: автомасштабирование Auto Scaling по CPU, алармы на короткие всплески нагрузки, поиск проблем производительности в продакшене. Метрики раз в минуту показывают пики, которые при усреднении за 5 минут сглаживаются. Для учебного или тестового сервера хватает бесплатного базового мониторинга.

### Задание 4. Подключение по SSH

![SSH](docs/screenshots/04-ssh-nginx.png)
_`ssh -i ~/.ssh/maxsplavski-keypair.pem ec2-user@35.159.38.203`: имя хоста `ip-172-31-19-131` и `systemctl status nginx` - `active (running)`._

> **Почему для входа на экземпляр EC2 используется ключ, а не пароль?**
> Пароль можно подобрать перебором, а публичный сервер с открытым 22 портом постоянно сканируют боты. Приватный ключ ED25519 подобрать практически невозможно, он не передаётся по сети (сервер проверяет только подпись), а на сервере хранится лишь публичный ключ, утечка которого не опасна. AWS сам кладёт публичный ключ в `~ec2-user/.ssh/authorized_keys` при запуске, а вход по паролю в AL2023 по умолчанию выключен.

> **Чем `Stop` отличается от `Terminate`? За что вы продолжаете платить, пока экземпляр остановлен?**
> `Stop` выключает виртуальную машину, но сохраняет её: корневой том EBS с данными остаётся, экземпляр можно снова запустить (на другом хосте и с новым публичным IP). `Terminate` удаляет экземпляр навсегда, и корневой том EBS по умолчанию удаляется вместе с ним. Пока экземпляр остановлен, оплата за вычисления не идёт, но продолжается оплата за тома EBS и снапшоты, а также за Elastic IP, если он закреплён.

> **Почему пароль к базе данных хранится в файле `.env` на сервере, а не в коде в репозитории? Почему публичный репозиторий безопасен для этого приложения?**
> Репозиторий публичный: всё, что в него попало, может прочитать кто угодно, и это остаётся в истории git навсегда, даже если файл потом удалить. Пароль относится к конкретному окружению, а не к коду, поэтому его держат в `.env` на сервере, доступном только владельцу и PHP-FPM. Публичный репозиторий безопасен, потому что в нём только код без секретов; к тому же PostgreSQL слушает только `localhost`, порт 5432 закрыт Security Group, а знание кода не даёт доступа к данным.

## Контрольные вопросы

**1. Как проходит запрос от браузера до базы данных в вашем развёртывании? Какую роль играет каждая программа?**
Браузер отправляет HTTP-запрос на публичный IP, порт 80; Security Group пропускает его к экземпляру. nginx принимает запрос: статические файлы (`css`, `js`) из `public/` отдаёт сам, а всё остальное через `try_files` передаёт в `index.php` и по FastCGI через unix-сокет `/run/php-fpm/www.sock` в PHP-FPM. PHP-FPM выполняет код приложения от имени `apache` и через PDO делает SQL-запросы к PostgreSQL на `localhost:5432`. Готовый HTML возвращается по той же цепочке обратно в браузер.

**2. Почему сервер может скачивать код из репозитория, но не может отправлять в него изменения? Почему для сервера это правильно?**
Репозиторий публичный, поэтому чтение по HTTPS доступно без учётных данных, а запись требует входа в GitHub с правами в организации. Таких учётных данных (токена, SSH-ключа) на сервере нет. Это принцип наименьших привилегий: если сервер взломают, злоумышленник не сможет подменить код в репозитории и через следующий деплой распространить вредоносный код.

**3. Что произойдёт с загруженными пользователями файлами, если удалить экземпляр EC2? Как это связано с тем, что вы знаете об EBS?**
Файлы лежат в `storage/uploads`, а база PostgreSQL в `/var/lib/pgsql` - всё на корневом томе EBS экземпляра. У корневого тома по умолчанию включён `DeleteOnTermination`, поэтому при Terminate том удалится вместе с файлами и базой, и данные будут потеряны безвозвратно (при Stop том сохраняется). Чтобы этого избежать, нужны снапшоты EBS или отдельный том, а правильнее - вынести базу на отдельный сервер или в RDS, а файлы в S3, что и делается в следующих работах.

**4. Что общего у вашего `deploy.sh` с тем, что делают системы CI/CD? Чего в вашем процессе ещё не хватает?**
Как и CD-конвейер, скрипт берёт код из репозитория как единственного источника, выполняет одинаковые шаги в фиксированном порядке (получение кода, установка зависимостей, миграции, перезапуск), останавливается при ошибке и сообщает, какая версия выпущена. Не хватает автоматического запуска по `git push`, этапа CI со сборкой и тестами (хотя бы `php -l`), проверки после деплоя с автоматическим откатом, атомарной выкладки без простоя, журнала выпусков и раздельных окружений (staging / production).

## Вывод

В работе с нуля поднят сервер Amazon EC2 в `eu-central-1`: экземпляр с ключом ED25519, Security Group с минимально необходимыми правилами и скриптом User data. Изучены инструменты диагностики (status checks, CloudWatch, system log, снимок экрана), выполнено подключение по SSH и выкладка статического сайта через `scp`. Во второй части на тот же экземпляр развёрнуто монолитное приложение TimeCapsule (nginx + PHP-FPM + PostgreSQL), код которого сервер забирает из публичного репозитория GitHub. Выпуск версий автоматизирован скриптом `deploy.sh`, запускаемым по SSH. На практике проверены выпуск новой версии, поломка и откат через `git revert`. Эксперимент показал ограничения подхода: неатомарная выкладка и `/health`, который не замечает ошибку в шаблоне. Решение и альтернативы зафиксированы в ADR.
